## Grype contributions

In the final month of my JOSA OpenLab apprenticeship, I investigated one issue and reviewed five pull requests from my Grype contribution proposal. The issue investigation led to a follow-up PR in Vunnel, and one of my review suggestions was incorporated into a Grype PR.

### [Issue #3530](https://github.com/anchore/grype/issues/3530)

This issue reported a possible false positive for `CVE-2025-35036` in a standalone Red Hat build of Hibernate Validator. I compared the SP1 and SP2 Maven sources and ran a local Java probe with a default `ValidatorFactory` to see how each version handled custom constraint violation messages. SP1 evaluated `${7 * 7}` to `49`, while SP2 left the expression literal. The source comparison and probe did not support the claim that the exact SP1 artifact in the report contained the backported fix. I documented the results and asked which version was used in the reproduction. [Issue comment](https://github.com/anchore/grype/issues/3530#issuecomment-6532220988)

I also traced how Grype uses RPM ownership to associate a JAR with an installed RPM. Copying a standalone JAR into an image does not create an RPM ownership record for it. `RHSA-2025:10925` identified a fixed EAP 7.4 RPM, and I found no evidence in that advisory that the standalone SP1 Maven artifact contained the same fix.

While tracing the advisory data, I found a separate coverage gap in Vunnel. Its RHEL product-name parser skipped EAP 7.4 RPM affected-release entries. I implemented conditional imports and added regression tests for conflicts between EAP products represented in the input. All 178 RHEL provider tests passed, along with Ruff and `git diff --check`. I opened a [PR](https://github.com/anchore/vunnel/pull/1429) for the RPM coverage gap and asked how Vunnel should preserve which EAP stream each record applies to.

### [PR #3601](https://github.com/anchore/grype/pull/3601)

I traced how Rust package source information reaches the matcher from `Cargo.lock` and from audit metadata embedded in compiled binaries. To isolate the matcher, I passed it synthetic audit-binary metadata for a local package and a `crates.io` control with the same name and version. The local package still matched the mock registry advisory, and the `crates.io` control returned its expected match.

The experiment covered the matcher with synthetic metadata. A full scan of the original `/usr/libexec/zed` binary was outside the test. I [included](https://github.com/anchore/grype/pull/3601#pullrequestreview-5734761686) the reproducer and asked whether the audit-binary path could be tracked separately.

### [PR #3633](https://github.com/anchore/grype/pull/3633)

I reviewed how the NVD transformer handles a `disputed` tag when `vulnStatus` is missing. I added a case for that combination, and it passed on the PR. As a temporary local change, I moved the nil-status check ahead of the disputed-tag check. The new case failed because it returned `Unknown` instead of `Disputed`, while all seven existing cases still passed.

I [suggested](https://github.com/anchore/grype/pull/3633#pullrequestreview-5772525652) adding the case to `TestGetVulnStatus`. The PR author added the test case in this [commit](https://github.com/anchore/grype/pull/3633/commits/185fc5914190431a67491f80febc9b1f19055f08).

### [PR #3327](https://github.com/anchore/grype/pull/3327)

I traced the RapidFort marker through `ApplySelectionPolicy` to understand how Grype selects the RapidFort matcher for curated images and which matcher handles upstream distribution findings after the switch. The [review](https://github.com/anchore/grype/pull/3327#pullrequestreview-5812036734).

### [PR #3584](https://github.com/anchore/grype/pull/3584)

I built a Wolfi image with `rclone` so I could reproduce the post-filter counting problem using public packages. I used the same image and vulnerability database for the baseline and PR builds. The JSON reports each contained 171 matches, and the match identities I compared were identical. The CLI severity total changed from 173 to 171. Comparing the two outputs let me isolate the discrepancy to reporting for this scan.

I used a separate teardown harness to check whether the progress UI could retain a stale snapshot after the monitor’s counters had been corrected. The harness reproduced that behavior on both builds, so I treated it separately from the counter fix. I [submitted](https://github.com/anchore/grype/pull/3584#pullrequestreview-5815735747) the public reproducer and a VEX counter test suggestion.

### [PR #2849](https://github.com/anchore/grype/pull/2849)

I used one official advisory and an openEuler SP3 image to check whether a missing match came from advisory ingestion or from the scan itself. The `os` records generated by Vunnel gave me a working reference case. For `csaf-vex`, I found a Grype revision that could build the database from the record. Using the same image and database, I observed zero matches for `CVE-2025-9820` before applying the openEuler changes locally and one RPM match for that CVE afterward. The advisory was present in the database in both runs.

I also tested malformed RHEL release metadata because the PR changed version selection shared by other distributions. With `ExtendedSupport: true` and neither release version field passing validation, the base panicked during version comparison. The PR skipped the `>= 8.0` check and returned the `eus` channel. I [asked](https://github.com/anchore/grype/pull/2849#pullrequestreview-5819147669) which ingestion format was intended for openEuler and suggested a regression test for the intended RHEL channel behavior.
